# Пояснение к лабораторной работе №1

## Параллельное численное интегрирование

Документ описывает, как работает программа `Lab1.java`, что такое время выполнения, ускорение и эффективность, как проводятся измерения и что означают полученные результаты.

---

## 1. Постановка задачи

Нужно численно вычислить определённый интеграл

$$
I = \int_a^b f(x)\,dx
$$

Здесь `f(x) = sin(x)`, `a = 0`, `b = π`. Точное значение известно:

$$
\int_0^{\pi} \sin(x)\,dx = 2
$$

Это значение используется для проверки корректности.

### Метод средних прямоугольников

Отрезок `[a, b]` разбивается на `N` равных частей. Шаг разбиения:

$$
h = \frac{b-a}{N}
$$

Середина `i`-го отрезка:

$$
x_i = a + \left(i + \tfrac{1}{2}\right)h
$$

Приближённое значение интеграла:

$$
I_N = h \sum_{i=0}^{N-1} f(x_i)
$$

Чем больше `N`, тем точнее результат, но тем больше вычислений (дольше работа).

В коде `N` — это переменная `n`, а шаг `h` и суммирование реализованы в функциях `integrateSequential` и `SumWorker.run`.

## 3. Последовательная версия

```java
static double integrateSequential(double a, double b, long n) {
    double h = (b - a) / n;
    double sum = 0.0;
    for (long i = 0; i < n; i++) {
        sum += f(a + (i + 0.5) * h);
    }
    return sum * h;
}
```

Один поток проходит все `N` отрезков, накапливает сумму значений функции в серединах и умножает её на `h`. Это эталон для сравнения.

## 4. Параллельная версия

### Идея

Диапазон из `N` отрезков делится между `p` потоками. Каждый поток обрабатывает **свой непрерывный диапазон** и копит **локальную сумму**. Затем локальные суммы складываются.

```
0 --------------------------------------------------------------- N
|--------------|--------------|--------------|--------------|
   Поток 0        Поток 1        Поток 2        Поток 3
```

```
localSum0 + localSum1 + localSum2 + localSum3 = total
result = total * h
```

### Поток-вычислитель

```java
static final class SumWorker extends Thread {
    ...
    @Override
    public void run() {
        double local = 0.0;
        for (long i = start; i < end; i++) {
            local += f(a + (i + 0.5) * h);
        }
        partial = local;   // локальная сумма потока
    }
}
```

Каждый поток хранит своё `partial` — отдельную переменную, к которой не обращаются другие потоки. Поэтому **не требуется синхронизация на каждой итерации**.

### Распределение работы и объединение

```java
for (int t = 0; t < threads; t++) {
    workers[t] = new SumWorker(a, h, n * t / threads, n * (t + 1) / threads);
    workers[t].start();
}
...
for (SumWorker w : workers) {
    w.join();          // ждём завершения потока
    total += w.partial; // складываем локальные суммы
}
```

- Поток `t` обрабатывает отрезки от `n*t/threads` до `n*(t+1)/threads`.
- Диапазоны не пересекаются и полностью покрывают `[0, N)`, поэтому **объём работы не меняется** при изменении числа потоков.
- `join()` заставляет главный поток дождаться окончания каждого рабочего потока.

### Почему не синхронизировать каждое сложение

Плохой вариант:

```java
for (...)
    synchronized (...) { total += ...; }
```

Тогда все потоки всё время конкурируют за одну переменную, простой занимает больше времени, чем сама работа, и выигрыш теряется. Локальные суммы + объединение в конце — правильный подход.

## 5. Как измеряется время

### Таймер

```java
long start = System.nanoTime();
result = integrator.integrate(A, B, n, threads);
long end = System.nanoTime();
times[i] = (end - start) / 1_000_000_000.0;   // наносекунды -> секунды
```

Замеряется **только само вычисление**, без подготовки. `System.nanoTime()` — монотонные наносекунды, подходят для измерения интервалов.

### Прогрев

```java
for (int i = 0; i < warmupRuns; i++) {
    integrator.integrate(A, B, n, threads);
}
```

Первые запуски в JVM медленнее: классы загружаются, JIT-компилятор оптимизирует «горячий» код. Такие запуски не учитываются.

### Несколько измерений и медиана

Делается `measureRuns` (по умолчанию 5) замеров. Результаты сортируются, берётся **медиана** — средний по порядку элемент:

```java
Arrays.sort(sorted);
double median = (measureRuns % 2 == 1)
        ? sorted[measureRuns / 2]
        : 0.5 * (sorted[measureRuns / 2 - 1] + sorted[measureRuns / 2]);
```

Дополнительно хранится **минимум** `sorted[0]`.

- **Медиана** устойчива к случайным всплескам (другие процессы, планировщик).
- **Минимум** показывает лучшее достижимое время без помех.
- Один запуск недостаточен — результат слишком шумный.

## 6. Ускорение

**Ускорение** показывает, во сколько раз параллельная версия быстрее базовой:

$$
S_p = \frac{T_1}{T_p}
$$

- `T_1` — время базового варианта;
- `T_p` — время при `p` потоках.

В программе за базу берётся параллельный запуск с **1 потоком** (`t1`), поэтому строка «1 поток» всегда даёт `1.000`, а «2 потока» — примерно `2`, но меньше из-за накладных расходов.

```java
double speedup = t1 / par[i].median;
```

Идеальное ускорение при `p` потоках равно `p`. На практике оно меньше: часть работы выполняется последовательно, есть затраты на создание потоков и объединение результатов.

Пример: время 1 потока `0.0712 с`, время 4 потоков `0.0181 с`:

$$
S_4 = \frac{0.0712}{0.0181} \approx 3.93
$$

---

## 7. Эффективность

**Эффективность** показывает, насколько полно используются потоки:

$$
E_p = \frac{S_p}{p} \cdot 100\%
$$

```java
double efficiency = speedup / p * 100.0;
```

- Идеальные `100%` означают линейное ускорение (`S_p = p`).
- Чем ближе к `100%`, тем меньше накладных расходов.
- С ростом числа потоков эффективность обычно падает.

Пример: `S_4 ≈ 3.93` при `p = 4`:

$$
E_4 = \frac{3.93}{4} \cdot 100\% \approx 98.1\%
$$

---

## 8. Проверка корректности

Обе версии должны давать одно и то же математическое значение (`2.0`). Сравнение — с допуском:

```java
Math.abs(result - EXACT) < EPS      // EPS = 1e-10
```

Результаты не обязаны совпадать бит-в-бит: порядок сложения `double` влияет на округление:

$$
(a+b)+c \ne a+(b+c)
$$

Допуск одинаков для всех версий и всех `N`.

## 9. Как проводится эксперимент

`main` вызывает `runForN(n)` для каждого `N` из `nValues`. Внутри:

1. измеряется последовательная версия (справочно);
2. измеряются параллельные версии для всех `threadCounts` (1, 2, 4, 8, 16, 32, 64);
3. для каждой строки считаются ускорение и эффективность;
4. печатается таблица:

```
потоки   время_с      мин_с        ускорение    эффективность  корр
1        0.071205     0.070924     1.000        100.00         OK
2        0.035886     0.035740     1.984        99.21          OK
...
```

Важное условие: при сравнении разных чисел потоков используется **одно и то же `N`** (объём работы одинаков).

## 11. Что показывают результаты

На 16-ядерной машине (16 логических процессоров):

| Наблюдение | Значение |
|------------|----------|
| Минимальное время | при **16 потоках** |
| Максимальное ускорение | ≈ **7.65** |
| Эффективность на 16 потоках | ≈ **48%** |
| Эффективность на 2 потоках | ≈ **95–100%** |

- Время падает при росте потоков до ~16, затем выходит на плато и даже растёт.
- После исчерпания физических ядер добавление потоков даёт только переключения контекста и накладные расходы.
- Крупная задача (`N = 10⁹`) масштабируется лучше мелкой, потому что фиксированные накладные расходы «размазываются» по большему объёму вычислений.

## 12. Краткие выводы

1. **Время** уменьшается с ростом числа потоков до количества ядер, затем стабилизируется.
2. **Рост потоков не всегда ускоряет**: после ~16 время может расти.
3. **Ускорение меньше числа потоков** из-за накладных расходов и части последовательной работы.
4. После исчерпания ядер выигрыш пропадает: переключения контекста, управление потоками, объединение результатов, другие процессы.
5. **Оптимум совпал с числом логических процессоров** (16).
6. При увеличении `N` время растёт, но эффективность распараллеливания обычно выше.
